# specrelay 执行

实现当前的 specrelay 变更。

## 条目类型与上下文

对于 small 工作，阅读 `brief.md`、`acceptance.json` 和 `tests/`，如存在 `proposal.md` 也一并阅读。对于 standard 工作，还要阅读完整的 `proposal.md`；在涉及架构决策、历史测试冲突或验收覆盖缺口时，查阅 `design.md` 和 `spec.md`。small 提案不会降低测试要求，也不免除维护规格的责任。

## 可选的外部技能

单独安装的 Matt Pocock 技能可以辅助实现。它们不由 `specrelay install` 安装；请检查可用性，若不存在则回退到本流程。

- `/implement` 和 `/tdd`：在保留提案测试并使新增内容与 `acceptance.json` 对齐的前提下，使用红-绿-重构。
- `/code-review`：在独立 QA 之前，同时审查工程质量和规格符合度；通过自查和修复处理发现的问题。
- `/prototype`：用一次性原型调查被证伪的契约假设。如果获授权的契约发生变化，同步更新其规格、验收和测试，并记录原因。原型代码不会自动成为交付代码。
- `/diagnosing-bugs`：诊断持续存在的缺陷、回归或原因不明的失败，然后在范围内补充相关的回归覆盖。
- `/codebase-design`：用作共享的设计词汇，不能替代实现责任。

外部技能不能绕过或削弱验收契约。调用其斜杠命令并遵循其自身流程。契约变更需要用户意图发生变化，并同步规格、验收和测试。

## 流程

1. 在工作流启动前确认提案已提交。SpecRelay 会封存 `delivery_base_head`；执行、审计、修复和测试在启动后不得创建或改写提交。
2. 阅读简报、验收契约、提案测试和完整的意图来源。不要仅凭 `acceptance.json` 和测试推断意图。
3. 先运行创建阶段的契约测试。初始失败应表明行为缺失，而不是语法、路径或环境故障。
4. 将每个覆盖条目和必需断言与提案的成功标准逐一比对。配置字符串、文件/脚本存在、HTTP 状态、元素存在、日志子串或仅退出成功，都不能确立一项行为或运行时保证。推进前加强薄弱的行为覆盖并记录原因；不要削弱预期结果。
5. 实现满足提案的最小可验证变更。
6. 运行受影响的测试以及所有 `acceptance.json.required_tests` 命令。
7. 在独立 QA 之前，显式运行仓库的 pre-commit hook 入口，且不创建临时提交。应用其修改并重新运行，直到没有文件发生变化。
8. hooks 稳定后，重新运行受影响的测试、必需测试和验证命令，使证据对应最终内容。
9. 将动态计划保存在执行器的 Todo 或运行时状态中。报告变更、验证情况和剩余风险。
10. 告知 `fix-code` 或 `fix-webapp`：它们正在 SpecRelay 内工作，应修改代码和测试并收集证据，但最终提交由 `specrelay-archive` 创建。

使用以下命令检查提案的提交状态：

```sh
git log --oneline -- docs/changes/<change>/
```

如有必要，在启动 SpecRelay 之前提交提案，使用显式路径，并以 `Proposal draft: <change>` 作为提交信息。工作流启动后，不要添加此类提交，也不要 amend、rebase 或 squash。

## 实现边界

- 遵循当前提案和最新的获授权用户意图。用真实断言检查每项成功标准，而不是利用验收覆盖的空白。
- 薄弱契约包括：当目标是行为、语义或运行时保证时，对配置、脚本、文件、HTTP 状态、元素、子串或退出码进行表面检查。静态夹具和 mock 结果不能替代真实业务流程。
- 审查 `tests/specs/` 和根 `tests/` 中相关的历史测试。按能力组织规格测试。如果新意图使旧预期失效，更新这些预期，并在设计或交付说明中解释冲突。
- 不要为了让实现通过而删除、跳过、削弱或绕过创建阶段的测试或 `acceptance.json`。
- 要求在 `test-results/` 下跟踪临时截图、trace 或运行时日志属于契约错误。应一致地修正映射；最终证据只有在 `tests/evidence/proposals/<change>/` 下才可跟踪。不要强制添加被忽略的输出。
- 当用户更改验收标准时，同步 `spec.md`、`design.md`、`acceptance.json` 和测试，并在继续实现前记录原因。
- 按需添加真实项目测试。新增契约内容应放在 `docs/changes/<change>/tests/` 下；回归和端到端测试可以使用现有的根测试布局。同步更新验收映射。
- 除非用户明确要求且提案记录了相关限制，否则不要 mock API 或数据库、伪造认证、硬编码成功结果，或仅依赖 HTTP 200。
- 不要向 `tests/` 添加占位文档。不要创建或修改 `task.md` 或其他受跟踪的动态任务列表；使用 Todo 或运行时状态。
- 执行、审计、修复和测试都不提交。归档会在 `delivery_base_head` 之后创建一个完整的交付提交。
- 找到声明的 hook 入口（项目脚本、pre-commit、lefthook 或 husky）。在 QA 前运行它，应用修改，然后在无改动的情况下再次运行。如果它仍持续修改文件，留在当前阶段并诊断。
- 保持 `test-results/` 为临时目录。稳定的预期快照可以按项目惯例跟踪；实际运行结果不得冒充预期基线。
- 演练 `delivery_report.scenarios` 中的每个用户路径，并收集易于理解的证据。Web 证据必须展示操作和页面结果；CLI 证据必须展示真实输入、输出和业务状态变更。
- 视频、截图和 trace 必须是真实可读的文件。echo/printf 字符串、退出码、HTTP 200、元素存在、测试通过消息和哈希不能替代用户证据。
- 修复的前后证据必须使用相同的入口、角色、数据和场景，并清晰展示失败行为变为可用。

## 长时间运行的演示

在前台运行 `paper-orchestra-production-live` 等长时间演示，让 stdout/stderr 对终端或工作流运行器可见。不要使用 `nohup ... &`、`setsid ... &`、shell 后台作业，也不要重定向日志后再 sleep 轮询。不要用 `sleep N && tail -f log` 让 pi 节点静默。

同步等待，并将进度输出保留为 go-dag 心跳。如果某个阶段可能超过五分钟没有输出，让演示本身定期输出进度，以免该节点看起来停滞。

## 退出标准

范围内的实现已完成，运行时规划已收敛。创建阶段的契约通过；相关回归、端到端和包测试已运行，且记录了命令与结果。没有绕过任何测试或验收边界。任何已变更的历史预期都有与新意图冲突的解释。

在最终 QA 前 hooks 已具备幂等性，随后的必需测试和验证均通过。每个提案成功标准都有有意义的验收覆盖，或有明确记录说明排除项及其风险承担者。行为变更必须包含相应的实现或架构；仅靠表面配置的合规是不完整的。

每个声明的用户场景都已用真实可读的证据演示。报告实现、测试变更、历史测试更新、命令和剩余风险。不要把通过的旧回归当作新行为的证明，也不要把验收遗漏当作忽略提案的许可。
